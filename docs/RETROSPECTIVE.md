## Keep — 잘한 것

- **돈이 걸린 판단을 LLM 밖에 둔 것.** 상품 선택은 최저 단가 규칙, 결제 승인은 `policy.ts` 결정론 엔진이고, Gemini는 선택 사유 2문장만 쓴다. Gemini 크레딧이 소진된 2026-09-28 재측정에서도 결제 흐름은 템플릿 사유로 그대로 돌았다. LLM이 실패해도 결제 판단이 바뀌지 않는다.
- **자금이 움직이기 전에 거절하는 구조.** 서명·만료·범위·카트·예산 검사를 402 발급 **전에** 한다. 위반하면 403으로 끝나고 돈이 움직이지 않는다. PR #1의 예산 예약도 이 원칙을 402 발급 시점까지 끌어온 것이다.
- **주문과 결제를 온체인에서 1:1로 묶은 것.** 주문마다 새 nonce를 Memo에 넣고 서버가 대조한다. 증빙 tx는 제출 두 달 뒤에도 devnet에서 `finalized`로 조회된다.
- **정직 고지를 남긴 것.** 제출 직후 README에 AP2/A2A 축약 구현, 서버가 키를 보관하는 데모 한계, 파일 DB 한계를 적었다. 사후 점검에서 어디부터 의심할지 정하는 출발점이 됐다.
- **사후 수정을 테스트 먼저, 리뷰 분리로 한 것.** 재현 테스트를 먼저 올려 6건 실패를 확인하고 고쳤다. 작성과 분리한 보안 리뷰가 내 수정이 만든 퇴행을 머지 전에 잡았다.

## Problem — 아쉬운 것 (구체적 결과와 함께)

- **"리플레이 차단"을 강점으로 내세우면서 동시 요청을 한 번도 시험하지 않았다.** 순차 통합 테스트 20개가 전부 통과했지만, 같은 증빙을 동시에 보내면 1회 지불로 주문이 최대 10건 확정됐다. 예산 100 USDC 위임장으로 327.59 USDC까지 확정됐고, 순차 요청에서도 262.07 USDC가 주문 없이 이동했다([트러블슈팅 1·2](TROUBLESHOOTING.md)).
- **내 수정이 새 공격면을 열었다.** "지불 확인되면 미확정으로 기록" 경로가 위조 cart에도 열려 있어, 제3자가 남의 지불을 선점해 영구 409로 만들 수 있었다. 내 테스트가 전부 정당한 클라이언트 시나리오였기 때문이다([트러블슈팅 3](TROUBLESHOOTING.md)).
- **README가 코드보다 앞서 나갔다.** 아키텍처 다이어그램은 "Gemini 의사결정"이라고 했지만 선택은 최저가 규칙이었다. 스택에 레포에 없는 Playwright가 있었고, API 문서에는 없는 `GET /merchants/{id}`가 있었다. 풀사이클 "4.7~10.5초"는 로그에 4.7초가 없고 11.1초가 빠진 범위였다. 2026-09-28에 불일치 15건을 정정했다.
- **팀 역할 표기가 사실과 달랐다.** README 역할 표는 제출폼 초안에서 옮긴 것이었고, 두 번째 팀원의 커밋은 0건인데 "백엔드 — 온체인 결제·검증 엔진·QA"로 적혀 있었다. 제출 후 커밋 2개에 `Co-Authored-By`로 기여 표시를 붙이기도 했다. 이력은 고치지 않고 README에서 실제 확인된 사실만 적는 쪽으로 정정했다.
- **개발 과정이 git에 없다.** 약 3시간의 작업이 첫 커밋 하나(+7,274줄)에 들어갔다. 커밋 6개 중 3개는 제출 후, 2개는 마감 후다(전부 문서). 커밋 `344147d`는 메시지와 실제 변경 파일이 달라 "베이글 사고를 고친 커밋"을 링크로 보일 수 없다.
- **데모 배포의 위생.** 무인증 공개 엔드포인트(에이전트 실행·가맹점 등록)가 떠 있었고, 심사 뒤 정리하기로 한 라이브를 최소 인스턴스 1로 약 8주간 켜 두었다(2026-09-28 최소 인스턴스 0으로 변경). 누구나 "카페 베이글" 가맹점을 등록해 기본 목표의 낙찰을 가로챌 수 있다는 것도 사후에 재현했다.
- **재측정할 수 없는 수치를 남겼다.** devnet faucet은 429, Gemini 선불 크레딧은 소진 상태라 devnet + Gemini 조건의 풀사이클과 PR #1의 devnet 전후 비교를 재지 못했다.

## Try — 다시 만든다면

| 영역 | 당시 선택 | 지금이라면 | 이유 |
|---|---|---|---|
| 멱등성·경합 | 파일 DB, 요청 시작 시 스냅샷으로 리플레이 검사 | 첫날부터 공유 DB의 유니크 제약(tx 서명, nonce)과 트랜잭션으로 check-and-set | 프로세스 내 잠금은 인스턴스가 늘면 무의미하다. 결제는 DB 제약이 최후 방어선이어야 한다 |
| 예산 집행 | 확정 시점에 한 번 더 검사 | 402 발급 시 예약 → 확정 시 집행 → 만료 시 해제를 처음부터 상태 모델로 | 확정 시점 검사는 지불 후 거절을 만든다 |
| 테스트 계획 | 순차 네거티브 테스트 | 동시성(K=10)·적대적 입력(위조 cart, 품목 바꿔치기)을 테스트 계획 1장에 | "리플레이 차단"을 주장하려면 동시 리플레이를 검사해야 한다 |
| 실패 처리 | 파싱 실패 시 빈 DB (fail-open) | 보안 상태 저장소는 fail-closed, 원자 교체 저장 | 빈 DB는 리플레이 방어를 지운다 |
| README | 심사 기준 대응 문구 위주, 마감 직전 수정 | 코드에서 확인되는 것만, 수치마다 측정 명령·조건 | 첫 화면이 틀리면 나머지도 의심받는다 |
| 커밋 | 작업 폴더에서 3시간 뒤 한 번에 커밋 | 기능 단위 커밋과 PR, 에이전트 세션도 단계마다 커밋 | "무엇을 언제 고쳤는가"를 증명할 수 있어야 한다 |
| 데모 배포 | 무인증 공개, 상시 웜 인스턴스 | 데모 토큰·rate limit, 최소 인스턴스 0, 심사 종료일에 정리 알림 | 비용과 악용 경로를 같이 닫는다 |
| 프로토콜 | AP2·x402·A2A 모양만 차용한 자체 구현 | 공개 x402 facilitator나 SDK가 있으면 우선 사용, 없으면 "구조 차용"을 첫 화면에 명시 | 자체 구현은 표준 준수 여부를 증명하기 어렵다 |
